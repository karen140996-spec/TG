# Постоянный запуск и перенос на VPS

## Минимальный сервер

Linux x86_64/arm64, 1 vCPU, 1 GB RAM, 10 GB диска, Docker Engine с Compose v2. Ориентир бюджета $5–10/месяц, не подтверждённый тариф конкретного провайдера. Домен, публичный веб-сервер и входящие порты приложению не нужны. Требуются SSH для обслуживания, исходящий HTTPS к api.telegram.org и доступ к Docker Hub для сборки. Не покупайте сервер до выбора региона, провайдера и способа оплаты.

## Подготовка файлов и секрета

Перенесите проект по SSH или через Git. Сейчас исходники находятся в рабочей среде; наличие файлов здесь не означает, что они опубликованы в GitHub. Не переносите `.git`, `.env`, `.secrets`, `.state` как часть исходного архива. Историю публикаций переносите отдельной резервной копией.

В каталоге проекта на VPS:

```sh
cp deploy/runtime.env.example .env
mkdir -p .secrets backups
chmod 700 .secrets backups
```

Проверьте значения `.env`: ID канала и владельца, час и часовой пояс. Токен в `.env` для Compose не нужен. Через доверенный редактор создайте `.secrets/telegram_bot_token` и вставьте только токен от BotFather. Не передавайте его аргументом shell-команды. После сохранения:

```sh
chmod 444 .secrets/telegram_bot_token
```

Файл смонтирован только для чтения; `444` нужен для чтения непривилегированным UID контейнера. Каталог `.secrets` должен оставаться `700`. В Docker build context ни секрет, ни очередь не входят. Не отправляйте `.secrets`, токен и `.env` в Git или чат.

## Перенос существующей очереди — ОБЯЗАТЕЛЬНО для нашего канала

Пост #1 уже опубликован, Telegram message_id=2. Чистый `seed` потеряет это знание. При переносе:

1. В боте `/pause`.
2. Остановить старый процесс издателя. Это делается непосредственно перед финальным переносом; не запускайте два long-polling клиента одного бота на разных машинах.
3. В старой среде сделать свежую копию (путь должен быть новым):

```sh
python app.py backup --output backups/publisher-transfer.sqlite3
```

4. Передать её по SSH в `backups/publisher-transfer.sqlite3` на VPS. Не публиковать копию в репозитории.
5. В каталоге проекта на VPS:

```sh
docker compose build
docker compose run --rm -T publisher python deploy/restore.py < backups/publisher-transfer.sqlite3
docker compose run --rm publisher python app.py status
```

В выводе пост #1 должен остаться `published`. Сверьте остальные статусы со свежей копией. Restore разрешён только в пустой volume и всегда включает паузу. Если база уже существует — остановитесь и выясните, откуда она. Не удаляйте volume для обхода проверки.

6. После проверки:

```sh
docker compose up -d
docker compose ps
docker compose logs --tail 30
```

Напишите `/queue` своему боту, получите ответ и проверьте, что первый пост отмечен опубликованным. Проверьте рестарт контейнера:

```sh
docker compose restart publisher
```

Ещё раз получите `/status` и `/queue`. Публикации остаются на паузе. Включать `/resume` только после явного решения владельца и наличия одобренных проверенных постов. `restart: unless-stopped` восстанавливает завершившийся процесс, но не заменяет мониторинг доступности сервера.

## Резервное копирование

Для рабочей SQLite нельзя полагаться на обычный `cp` открытого файла. Используйте SQLite backup:

```sh
docker compose exec -T publisher python app.py backup --output /app/.state/backup-YYYY-MM-DD.sqlite3
```

Замените YYYY-MM-DD на дату. Команда не перезаписывает существующий файл. Для выгрузки на хост:

```sh
docker compose cp publisher:/app/.state/backup-YYYY-MM-DD.sqlite3 backups/backup-YYYY-MM-DD.sqlite3
chmod 600 backups/backup-YYYY-MM-DD.sqlite3
```

Храните минимум одну копию вне VPS. Автоматическое расписание резервных копий в эту версию не включено. Не выполняйте `docker compose down -v`: это удалит очередь. Обычный `docker compose stop` её сохраняет.

## Проверки в облачной среде

Локальные тесты покрывают состояния согласования, повторный запуск, дневной лимит, неопределённую доставку, копирование/восстановление и блокировку второго процесса. Docker-сборка и локальные контейнерные проверки описываются в отчёте задачи; они не подтверждают работу на ещё не выбранном VPS. Контейнерные проверки не должны использовать токен действующего бота: параллельный long polling недопустим.
